# 수주/제안 온톨로지 구축 실행 설계서

작성 기준: `/home/minjoo/AX_서울펠로우/handoff-hanyang`  
대상 도메인: 수주/제안  
핵심 자료: NCS, PCF, O*NET, Shipley 자료, 수주 에이전트 자료  

## 1. 한 줄 결론

이 프로젝트는 **Layer 1 표준 온톨로지**, **Layer 2 수주/제안 도메인 온톨로지**, **에이전트 실행 온톨로지**를 각각 만든 뒤, 이들을 **alignment relation**으로 연결하는 방식으로 진행한다.

즉, 하나의 거대한 온톨로지를 억지로 만드는 것이 아니라 다음 구조를 만든다.

```text
Layer 1 Standard Ontology
NCS / PCF / O*NET 표준 직무·프로세스·역량
        ↓ alignment
Layer 2 Bid Proposal Domain Ontology
Shipley 기반 수주/제안 업무 개념·규칙·산출물
        ↓ grounding
Agent Execution Ontology
RFP 분석, Go/No-Go, 전략개발, ES, Storyboard, 제안서 생성 에이전트
```

JAO는 출발점이 아니다. JAO는 AX가 만든 참고 모델이므로, 최종 온톨로지의 상위 스키마로 채택하지 않고 에이전트/액션/도구 표현을 참고하는 보조 자료로만 사용한다.

## 2. 왜 세 개로 나누는가

세 자료층은 서로 다른 질문에 답한다.

| 구분 | 답하는 질문 | 대표 자료 | 대표 개념 |
|---|---|---|---|
| Layer 1 표준 온톨로지 | 이 업무는 어떤 표준 직무/프로세스/역량에 속하는가? | NCS, PCF, O*NET | `NCSUnit`, `PCFProcess`, `ONetTask`, `Competency` |
| Layer 2 도메인 온톨로지 | 수주/제안 업무는 실제로 어떤 규칙과 산출물로 진행되는가? | Shipley, Capture Plan, Decision Gate 자료 | `Opportunity`, `Requirement`, `HotButton`, `DecisionGate`, `BusinessRule`, `ArtifactSchema` |
| 에이전트 실행 온톨로지 | 어떤 에이전트가 어떤 순서로 어떤 규칙을 사용해 실행하는가? | `bid-agent.skill`, `shipley_full_agent_system.xlsx` | `Agent`, `AgentAction`, `Workflow`, `Trace` |

Layer 1만으로는 수주 업무의 실제 판단 규칙을 설명하기 어렵다. 예를 들어 PCF에는 `RFP/RFQ 검토`라는 표준 프로세스가 있지만, “RFP를 검토할 때 요구사항, 평가기준, 제출지시, 비공식 이슈를 어떻게 뽑아야 하는가”는 Shipley 자료와 에이전트 프롬프트에 있다.

반대로 Layer 2만 만들면 표준 직무 체계와 연결되지 않아 연구 확장성과 설명력이 약해진다. 따라서 둘 다 온톨로지로 만들고, 명시적 relation으로 연결해야 한다.

### 4.1 파일 출처 관리 방식

이 프로젝트에서는 파일을 그냥 “참고 자료”로만 두면 안 된다. 나중에 온톨로지 노드, 업무 규칙, 에이전트 액션이 어디에서 나왔는지 확인할 수 있어야 하므로, 모든 입력 파일을 `source_registry`에 먼저 등록한다.

각 파일은 최소한 다음 필드를 가진다.

```json
{
  "source_id": "SRC-SHIPLEY-AGENT-XLSX-001",
  "local_path": "수주제안/쉬플리 강의 등 자료/shipley_full_agent_system.xlsx",
  "source_family": "Shipley/AX derived",
  "origin_owner": "확인 필요",
  "origin_status": "AX 가공본으로 추정, 원천 확인 필요",
  "observed_metadata": {
    "creator": "openpyxl",
    "application": "Microsoft Excel Compatible / Openpyxl 3.1.5",
    "created": "2026-03-24T23:36:15Z",
    "modified": "2026-03-24T23:36:15Z"
  },
  "license_scope": "연구 내부 사용. 외부 공개 전 AX/Shipley 권리 확인 필요",
  "used_for": ["AEO", "BPDO"],
  "extraction_unit": "sheet/row/cell"
}
```

위 예시에서 중요한 점은 `shipley_full_agent_system.xlsx`를 곧바로 “Shipley 원문”이라고 단정하지 않는 것이다. 현재 파일 메타데이터상 생성자는 `openpyxl`이고, 폴더 위치와 내용상 Shipley 자료를 바탕으로 AX가 에이전트 시스템 형태로 가공한 내부 설계표로 보인다. 따라서 문서에는 **AX 가공본으로 추정하되 원천 확인 필요**라고 표시해야 한다.

파일별 출처 관리 표는 다음 형태로 유지한다.

| source_id | 파일 | 출처 판단 | 권리/공개 범위 | 온톨로지 사용처 |
|---|---|---|---|---|
| `SRC-NCS-UNIT-001` | `01_ncs/ncs_unit.json` | NCS 공공데이터 | 공개 가능, 출처 표기 권장 | L1SO `NCSUnit` |
| `SRC-PCF-MARKET-001` | `06_suju_focus/pcf_3.0_market_and_sell.json` | APQC PCF 기반 AX 가공본 | 연구 내부. 원문 재배포 불가 | L1SO `PCFProcess` |
| `SRC-ONET-001` | `03_onet/onet_occupations_full.json` | O*NET CC-BY 4.0 | 공개 가능, 출처 표기 필수 | L1SO `ONetTask` |
| `SRC-SHIPLEY-MATERIAL-001` | `수주제안/쉬플리 강의 등 자료/` | Shipley 교육/양식 자료 | 연구 내부. 외부 공개 불가 또는 확인 필요 | BPDO `BusinessRule`, `ArtifactSchema` |
| `SRC-SHIPLEY-AGENT-XLSX-001` | `shipley_full_agent_system.xlsx` | AX 가공본으로 추정, 원천 확인 필요 | 연구 내부. 외부 공개 전 확인 필요 | AEO `AgentAction`, `Workflow` |
| `SRC-BID-AGENT-SKILL-001` | `수주제안/수주 에이전트/bid-agent.skill` | AX 수주 에이전트 skill | 연구 내부/AX 자산 | AEO 7단계 baseline |

온톨로지 노드와 규칙에는 반드시 `sourceRef`를 넣는다.

```json
{
  "id": "bpdo://rule/go-no-go/strategic-fit",
  "type": "BusinessRule",
  "label": "전략 적합성 기반 Go/No-Go 판단 규칙",
  "sourceRef": {
    "source_id": "SRC-SHIPLEY-AGENT-XLSX-001",
    "locator": "sheet=Decision Gates; row=확인 필요",
    "extraction_method": "manual_review_plus_llm_extraction",
    "confidence": 0.72
  }
}
```

이렇게 하면 연구 결과를 설명할 때 “이 규칙은 Shipley/AX 자료의 어느 부분에서 왔고, 어떤 판단으로 온톨로지에 들어갔는가”를 추적할 수 있다. 특히 APQC, Shipley처럼 공개 제한이 있는 자료는 원문을 논문에 싣지 않더라도, `source_id`, 자료 유형, 추출 기준, 통계는 남길 수 있다.

## 8. Step 3: 업무 규칙 BusinessRule 추출

이 프로젝트의 핵심은 단순 entity-relation triple이 아니라 **업무 규칙**이다.

쉽게 말하면 `BusinessRule`은 “업무를 언제, 어떤 조건에서, 어떤 기준으로, 어떤 예외를 고려해, 어떤 산출물로 처리해야 하는가”를 표현하는 노드다.

일반 triple은 다음 정도만 표현한다.

```text
RFP -> contains -> Requirement
Proposal -> respondsTo -> Requirement
DecisionGate -> evaluates -> Opportunity
```

하지만 실제 에이전트가 일을 하려면 이것만으로 부족하다. 입찰 여부를 판단할 때는 다음 질문에 답해야 한다.

```text
언제 Go/No-Go 판단을 하는가?
무엇을 입력으로 봐야 하는가?
어떤 기준으로 판단해야 하는가?
예외 조건은 무엇인가?
어떤 산출물을 만들어야 하는가?
누가 승인해야 하는가?
근거는 어디에 남겨야 하는가?
```

이 질문들을 구조화한 것이 `BusinessRule`이다. 따라서 `BusinessRule`은 단순한 JSON 양식이 아니라 BPDO, 즉 수주/제안 도메인 온톨로지의 핵심 클래스다.

규칙은 다음 frame으로 추출한다.

```json
{
  "id": "",
  "ruleType": "decision | validation | sequencing | approval | exception",
  "actor": "",
  "trigger": "",
  "input": [],
  "preconditions": [],
  "decisionCriteria": [],
  "action": "",
  "output": [],
  "exceptions": [],
  "approvalRequired": [],
  "evidence": {
    "file": "",
    "pageOrSlide": "",
    "sourceSpan": ""
  },
  "confidence": 0.0
}
```

예시: Go/No-Go 판단 규칙

```json
{
  "id": "bpdo://rule/go-nogo-pwin-risk",
  "class": "BusinessRule",
  "ruleType": "decision",
  "trigger": "Pursuit Decision 단계 진입",
  "input": [
    "customerProfile",
    "requirementMatrix",
    "competitorProfile",
    "solutionFit",
    "costRisk"
  ],
  "decisionCriteria": [
    "customerRelationship",
    "solutionFit",
    "competitivePosition",
    "priceCompetitiveness",
    "pastPerformance",
    "resourceAvailability",
    "strategicFit"
  ],
  "action": "Pwin을 산출하고 Go / Conditional Go / No-Go를 권고",
  "output": [
    "PwinScorecard",
    "BidNoBidRecommendation",
    "RiskRegister"
  ],
  "exceptions": [
    "필수 자격 미충족 시 Pwin과 무관하게 No-Go",
    "수익성 하한 미달 시 Conditional Go 또는 No-Go"
  ],
  "evidence": {
    "file": "수주제안/수주 에이전트/bid-agent.skill",
    "prompt": "02-bid-decision.md"
  }
}
```

### 8.1 이 frame이 필요한 이유

이 frame은 LLM이 문서에서 규칙을 뽑을 때 아무 문장이나 요약하지 않도록 만드는 추출 틀이다.

예를 들어 Shipley 자료나 `bid-agent.skill`에는 “Pursuit Decision에서 고객 관계, 솔루션 적합성, 경쟁 위치, 리스크를 고려해 입찰 여부를 판단한다”는 식의 지식이 들어 있다. 이것을 그냥 문장으로 저장하면 에이전트가 매번 다르게 해석한다. 반대로 위 frame으로 저장하면 다음처럼 재사용할 수 있다.

| frame 필드 | 나중에 쓰이는 곳 |
|---|---|
| `trigger` | 어느 단계에서 이 규칙을 실행할지 결정 |
| `input` | 에이전트 Action Contract의 입력 조건으로 연결 |
| `preconditions` | 실행 전에 충족해야 할 조건으로 연결 |
| `decisionCriteria` | 판단 기준, 평가 체크리스트, 검증 항목으로 연결 |
| `action` | 에이전트가 수행해야 할 작업으로 연결 |
| `output` | 산출물 스키마와 연결 |
| `exceptions` | 리스크/예외 처리 규칙으로 연결 |
| `approvalRequired` | 사람 승인 또는 Decision Gate와 연결 |
| `evidence` | 출처 추적과 전문가 검수에 사용 |

즉, 이 frame은 “문서 속 암묵적 업무 노하우”를 에이전트가 사용할 수 있는 구조화된 규칙으로 바꾸는 장치다.

### 8.2 나중에 어떻게 연결되는가

`BusinessRule`은 혼자 존재하지 않는다. 이후 단계에서 다음처럼 연결된다.

```text
L1SO: PCF 3.5.3.5 전략·사업계획 검증
  <- operationalizes
BPDO: go-nogo-pwin-risk BusinessRule
  <- usesRule
AEO: make-bid-decision AgentAction
  <- recordedBy
Trace: 실제 Go/No-Go 실행 기록
```

그래프 관계로 쓰면 다음과 같다.

```text
(:BusinessRule)-[:OPERATIONALIZES]->(:PCFProcess)
(:BusinessRule)-[:REQUIRES_INPUT]->(:ArtifactSchema)
(:BusinessRule)-[:HAS_CRITERION]->(:DecisionCriterion)
(:BusinessRule)-[:HAS_EXCEPTION]->(:ExceptionCondition)
(:BusinessRule)-[:PRODUCES]->(:ArtifactSchema)
(:AgentAction)-[:USES_RULE]->(:BusinessRule)
(:Trace)-[:USED_RULE]->(:BusinessRule)
(:Trace)-[:USED_EVIDENCE]->(:Evidence)
```

Go/No-Go 예시에서는 다음처럼 연결된다.

| 연결 | 의미 |
|---|---|
| `go-nogo-pwin-risk` -> `PCF 3.5.3.5` | 이 규칙은 PCF의 전략/사업계획 검증 프로세스를 실제 판단 규칙으로 구현함 |
| `go-nogo-pwin-risk` -> `PwinScorecard` | 이 규칙을 실행하면 Pwin 점수표가 산출됨 |
| `go-nogo-pwin-risk` -> `RiskRegister` | 위험요소도 함께 기록해야 함 |
| `make-bid-decision` -> `go-nogo-pwin-risk` | 입찰결정 에이전트는 이 규칙을 반드시 사용해야 함 |
| `Trace` -> `go-nogo-pwin-risk` | 실제 실행에서 이 규칙을 사용했는지 검증함 |

따라서 `BusinessRule`은 세 역할을 한다.

1. Layer 2에서 수주/제안 업무 노하우를 구조화한다.
2. AEO에서 에이전트가 반드시 사용할 규칙으로 연결된다.
3. H2 평가에서 에이전트가 규칙을 지켰는지 검증하는 기준이 된다.

### 8.3 BusinessRule 구축 절차

BusinessRule은 한 번에 완성하지 않는다. 다음 순서로 만든다.

```text
원천 자료 등록
  -> 문서/시트/프롬프트 단위로 분할
  -> 규칙 후보 추출
  -> BusinessRule frame으로 구조화
  -> BPDO 용어로 정규화
  -> evidence/sourceRef 부착
  -> L1SO/BPDO/AEO와 연결
  -> 전문가 검수
  -> bpdo_rules.json으로 확정
```

#### 1단계: 원천 자료를 먼저 등록한다

모든 규칙은 반드시 출처를 가져야 한다. 출처가 없는 규칙은 온톨로지에 바로 넣지 않고 후보로만 둔다.

예:

| source_id | 원천 | 추출 단위 |
|---|---|---|
| `SRC-BID-AGENT-SKILL-001` | `bid-agent.skill` | prompt 파일, heading, 문장 |
| `SRC-SHIPLEY-AGENT-XLSX-001` | `shipley_full_agent_system.xlsx` | sheet, row, cell |
| `SRC-SHIPLEY-MATERIAL-001` | Shipley 강의/양식 | PDF page, PPT slide |

#### 2단계: 규칙 후보를 찾는다

문서에서 다음 표현이 나오면 BusinessRule 후보로 본다.

| 단서 | 규칙 유형 |
|---|---|
| “반드시”, “모든”, “누락 없이”, “검증한다” | `validation` |
| “판단한다”, “Go/No-Go”, “점수화”, “추천한다” | `decision` |
| “이후”, “다음 단계”, “선행 산출물” | `sequencing` |
| “승인”, “Gate”, “Review”, “검토” | `approval` |
| “미충족 시”, “불가하면”, “예외”, “조건부” | `exception` |

예를 들어 `bid-agent.skill`의 `01-rfp-analysis.md`에는 다음 규칙 후보가 있다.

```text
모든 요구사항을 추출하고 필수(Shall)/권고(Should)/선택(May)으로 분류
```

이는 단순 개념이 아니라 `RFP 분석 단계에서 무엇을 반드시 해야 하는가`를 말하므로 BusinessRule 후보가 된다.

#### 3단계: 후보 규칙을 atomic rule로 쪼갠다

한 문장 안에 여러 규칙이 섞이면 나눠야 한다.

예:

```text
RFP에서 모든 요구사항을 추출하고 필수/권고/선택으로 분류하며, 각 요구사항의 근거 위치를 남긴다.
```

위 문장은 최소 세 개 규칙으로 나눈다.

| atomic rule | ruleType |
|---|---|
| 모든 요구사항을 추출해야 한다 | `validation` |
| 요구사항을 Shall/Should/May로 분류해야 한다 | `validation` |
| 각 요구사항에는 원문 근거 위치가 있어야 한다 | `validation` |

이렇게 쪼개야 나중에 에이전트가 어떤 규칙을 지켰고 어떤 규칙을 어겼는지 평가할 수 있다.

#### 4단계: BusinessRule frame으로 구조화한다

예: RFP 요구사항 분류 규칙

```json
{
  "id": "bpdo://rule/rfp-requirement-classification",
  "class": "BusinessRule",
  "ruleType": "validation",
  "actor": "RFP Analysis Agent",
  "trigger": "RFP 분석 단계 진입",
  "input": [
    "RFPDocument"
  ],
  "preconditions": [
    "RFP 원문 또는 공고문이 제공되어야 한다"
  ],
  "decisionCriteria": [
    "요구사항 문장이 의무 표현을 가지면 Shall",
    "권장 표현을 가지면 Should",
    "선택 또는 가능 표현을 가지면 May"
  ],
  "action": "RFP의 모든 요구사항을 추출하고 Shall/Should/May로 분류한다",
  "output": [
    "RequirementMatrix"
  ],
  "exceptions": [
    "분류가 불확실한 요구사항은 assumption 또는 reviewNeeded로 표시한다"
  ],
  "approvalRequired": [
    "핵심 요구사항 누락 가능성이 있으면 제안 PM 검수"
  ],
  "evidence": {
    "source_id": "SRC-BID-AGENT-SKILL-001",
    "file": "수주제안/수주 에이전트/bid-agent.skill",
    "prompt": "bid-agents-v2/prompts/01-rfp-analysis.md",
    "sourceSpan": "모든 요구사항을 추출하고 필수(Shall)/권고(Should)/선택(May)으로 분류"
  },
  "confidence": 0.88
}
```

#### 5단계: BPDO 용어로 정규화한다

추출된 표현을 그대로 쓰면 안 된다. 같은 의미를 하나의 BPDO 노드로 맞춘다.

| 문서 표현 | BPDO canonical node |
|---|---|
| 요구사항 표, 요구사항 목록, Requirement Matrix | `bpdo://artifact-schema/requirement-matrix` |
| 입찰 여부, Bid/No-Bid, Go/No-Go | `bpdo://decision-gate/go-no-go` |
| 위험목록, 리스크표, Risk Register | `bpdo://artifact-schema/risk-register` |
| 평가표, 평가기준, 배점표 | `bpdo://artifact-schema/evaluation-criteria-list` |

#### 6단계: 온톨로지 관계로 연결한다

BusinessRule은 최소 네 방향으로 연결한다.

```text
BusinessRule -> L1SO 표준 프로세스
BusinessRule -> BPDO 개념/산출물
AgentAction -> BusinessRule
Trace -> BusinessRule
```

RFP 요구사항 분류 규칙의 연결 예:

```text
(:BusinessRule {id:"bpdo://rule/rfp-requirement-classification"})
  -[:OPERATIONALIZES]->
(:PCFProcess {id:"l1so://pcf/process/3.5.3.3"})

(:BusinessRule {id:"bpdo://rule/rfp-requirement-classification"})
  -[:PRODUCES]->
(:ArtifactSchema {id:"bpdo://artifact-schema/requirement-matrix"})

(:AgentAction {id:"aeo://agent-action/analyze-rfp"})
  -[:USES_RULE]->
(:BusinessRule {id:"bpdo://rule/rfp-requirement-classification"})
```

#### 7단계: 전문가 검수 대상으로 보낸다

모든 규칙을 같은 강도로 검수할 필요는 없다. 우선순위는 다음과 같다.

| 우선순위 | 대상 |
|---|---|
| P0 | Go/No-Go, No-Bid, 승인, 법적/계약 리스크 관련 규칙 |
| P1 | 요구사항 누락 검증, 평가기준 매핑, 가격/수익성 판단 규칙 |
| P2 | 문체, 제안서 표현, PT 구성 원칙 |

검수자는 다음만 판단하면 된다.

```text
이 규칙이 실제 업무적으로 맞는가?
출처 문장과 규칙 해석이 일치하는가?
너무 큰 규칙이면 더 작은 atomic rule로 쪼개야 하는가?
에이전트가 이 규칙을 실행 가능한가?
```

#### 8단계: 확정 규칙을 저장한다

검수된 규칙은 `bpdo_rules.json`에 저장하고, 연결 관계는 `bpdo_edges.json` 또는 `alignment_edges.json`에 저장한다.

```text
02_bpdo/
  bpdo_rules.json        # BusinessRule 본문
  bpdo_nodes.json        # Requirement, DecisionGate, ArtifactSchema 등
  bpdo_edges.json        # BusinessRule -> ArtifactSchema 등 도메인 내부 연결

04_alignment/
  alignment_edges.json   # BusinessRule -> PCF/NCS 등 표준 연결
```

최소 파일럿에서는 다음 5개 BusinessRule부터 구축한다.

| 우선순위 | BusinessRule | 원천 |
|---|---|---|
| 1 | RFP 요구사항 전체 추출 규칙 | `01-rfp-analysis.md` |
| 2 | 요구사항 Shall/Should/May 분류 규칙 | `01-rfp-analysis.md` |
| 3 | Go/No-Go Pwin 판단 규칙 | `02-bid-decision.md` |
| 4 | 필수 자격 미충족 시 No-Bid 플래그 규칙 | `02-bid-decision.md` |
| 5 | 평가항목 1:1 목차 매핑 규칙 | `05-storyboard.md` |

## 9. Step 4: Canonicalization

문서마다 같은 개념을 다르게 부른다. 이를 하나의 canonical node로 정리해야 한다.

| Canonical node | Alias |
|---|---|
| `Pursuit Decision` | 추진 여부 결정, 사업추진 결정, Go/No-Go |
| `Capture Plan` | 수주계획서, 수주 계획서 |
| `Win Strategy` | 수주전략, 이기는 전략, Winning Strategy |
| `Hot Button` | 핵심 이슈, 고객 핵심 관심사 |
| `Bidder Comparison Chart` | BCC, 경쟁사 비교표 |
| `Executive Summary` | ES, 제안 요약본 |

예시:

```json
{
  "canonicalId": "bpdo://artifact-schema/capture-plan",
  "canonicalLabel": "Capture Plan",
  "aliases": ["수주계획서", "수주 계획서", "CapturePlan"],
  "mergeReason": "모두 동일한 수주 기회 관리 산출물 구조를 지칭",
  "confidence": 0.94
}
```

## 10. Step 5: Alignment relation 구축

Alignment relation은 서로 다른 온톨로지를 그냥 붙이는 것이 아니라, **온톨로지 상의 명시적 관계로 연결하는 것**이다.

예를 들어 다음 세 개는 같은 업무를 서로 다른 관점에서 말한다.

```text
L1SO: PCF 3.5.3.3 RFP/RFQ 검토
BPDO: RFP 분석 업무 규칙
AEO: RFP Analysis AgentAction
```

이 셋을 하나의 노드로 합치면 의미가 흐려진다. 대신 relation으로 연결한다.

```text
l1so://pcf/process/3.5.3.3
  <- operationalizes
bpdo://rule/rfp-analysis-coverage
  <- usesRule
aeo://agent-action/analyze-rfp
```

대표 alignment relation:

| Relation | 의미 |
|---|---|
| `mapsToStandard` | BPDO 개념이 어떤 표준 노드와 대응되는지 |
| `operationalizes` | BPDO 규칙이 PCF 표준 프로세스를 실제 업무 절차로 구현함 |
| `requiresCompetency` | BPDO 업무가 어떤 NCS 능력을 필요로 하는지 |
| `similarToTask` | BPDO 업무가 어떤 O*NET task와 유사한지 |
| `usesRule` | AEO 에이전트 액션이 어떤 BPDO 규칙을 사용하는지 |
| `producesArtifact` | AEO 에이전트 액션이 어떤 BPDO 산출물을 만드는지 |

예시:

```json
{
  "from": "bpdo://rule/rfp-analysis-coverage",
  "predicate": "operationalizes",
  "to": "l1so://pcf/process/3.5.3.3",
  "rationale": "RFP/RFQ 검토 표준 프로세스를 요구사항, 평가기준, 제출지시, 비공식 이슈 추출 규칙으로 구체화",
  "confidence": 0.86
}
```

```json
{
  "from": "bpdo://strategy/win-strategy",
  "predicate": "requiresCompetency",
  "to": "l1so://ncs/unit/20010501-05",
  "rationale": "Win Strategy는 고객 요구, 경쟁사 분석, 제안 평가 우위 요소 도출을 포함하므로 NCS 수주전략수립과 연결됨",
  "confidence": 0.9
}
```

## 11. Step 6: 에이전트 실행 온톨로지 구축

초기에는 `bid-agent.skill`의 7단계를 기준으로 만든다.

여기서 헷갈리면 안 되는 점은 AEO가 두 부분으로 나뉜다는 것이다.

| 구분 | 의미 | 시점 | 예시 |
|---|---|---|---|
| 실행 전 틀, Action Contract | 에이전트가 어떤 입력을 받고, 어떤 규칙을 사용하고, 어떤 산출물을 만들어야 하는지 정한 틀 | 실행 전 | `analyze-rfp`는 RFP를 입력받아 BPDO의 RFP 분석 규칙을 사용하고 요구사항 매트릭스를 출력해야 함 |
| 실행 후 기록, Trace | 실제 실행에서 어떤 규칙, 근거, 문서 위치, 출력이 사용되었는지 남긴 기록 | 실행 후 | `analyze-rfp`가 RFP 12p, 18p를 근거로 요구사항 37개를 추출함 |

따라서 AEO는 단순한 로그가 아니다. 먼저 **Action Contract**를 정의해서 에이전트가 BPDO 지식을 어떤 방식으로 사용해야 하는지 정하고, 실행이 끝난 뒤 **Trace**를 남겨 실제로 그 틀을 따랐는지 검증한다.

### 11.1 실행 전 틀: Action Contract

각 `AgentAction`은 최소한 다음 항목을 가져야 한다.

| 항목 | 의미 |
|---|---|
| `inputSchema` | 이 액션이 받는 입력. 예: RFP 문서, 고객명, 사업분야 |
| `requiredRules` | 반드시 사용해야 하는 BPDO 업무 규칙 |
| `requiredEvidence` | 결과에 붙어야 하는 근거 유형. 예: RFP 페이지, Shipley 양식, Capture Plan 항목 |
| `outputSchema` | 만들어야 하는 산출물 구조 |
| `validationChecks` | 실행 후 통과해야 하는 검증 조건 |
| `nextAction` | 다음으로 넘어갈 수 있는 액션 |
| `humanReviewRequired` | 사람 검수가 필요한지 여부 |

예시는 다음과 같다.

```json
{
  "id": "aeo://agent-action/analyze-rfp",
  "class": "AgentAction",
  "label": {"ko": "RFP 분석"},
  "inputSchema": ["RFPDocument", "CustomerName", "BusinessDomain"],
  "requiredRules": [
    "bpdo://rule/rfp-analysis-coverage"
  ],
  "requiredEvidence": [
    "RFP page reference",
    "requirement text span"
  ],
  "outputSchema": [
    "RequirementMatrix",
    "EvaluationCriteriaList",
    "SubmissionInstructionList",
    "RiskList"
  ],
  "validationChecks": [
    "모든 핵심 요구사항에는 원문 근거가 있어야 한다",
    "평가기준과 제출지시는 요구사항과 분리되어야 한다",
    "근거 없는 추정은 risk 또는 assumption으로 표시해야 한다"
  ],
  "nextAction": "aeo://agent-action/make-bid-decision",
  "humanReviewRequired": true
}
```

이 정의가 있어야 에이전트가 그냥 RFP 요약문을 만드는 것이 아니라, 온톨로지에 정의된 업무 규칙에 맞춰 구조화된 산출물을 만들게 된다.

### 11.2 실행 후 기록: Trace

실행이 끝나면 실제 사용 내역을 `Trace`로 남긴다.

```json
{
  "id": "aeo://trace/run-20260622-001/action-1",
  "class": "Trace",
  "action": "aeo://agent-action/analyze-rfp",
  "usedRules": [
    "bpdo://rule/rfp-analysis-coverage"
  ],
  "usedEvidence": [
    {
      "source_id": "SRC-RFP-001",
      "locator": "page=12",
      "text_span": "제안사는 보안 인증 자료를 제출해야 한다"
    }
  ],
  "producedOutputs": [
    "artifact://run-20260622-001/requirement-matrix",
    "artifact://run-20260622-001/evaluation-criteria"
  ],
  "validationResults": [
    {
      "check": "모든 핵심 요구사항에는 원문 근거가 있어야 한다",
      "status": "pass"
    }
  ]
}
```

정리하면 다음과 같다.

```text
BPDO = 업무 지식과 규칙
AEO Action Contract = 에이전트가 그 지식을 사용해야 하는 방식
AEO Trace = 실제로 그 지식을 어떻게 사용했는지에 대한 기록
```

H2 실험에서는 이 구조가 중요하다. 일반 RAG 에이전트는 “좋은 답변을 했는가”만 볼 수 있지만, 온톨로지 결합 에이전트는 “정해진 업무 규칙을 사용했는가, 근거를 남겼는가, 검증 조건을 통과했는가”까지 평가할 수 있다.

## 12. Step 7: Graph DB 적재

```text
(:PCFProcess)-[:SUB_PROCESS_OF]->(:PCFProcess)
```

## 13. Step 8: Human Review Queue

자동 추출 결과는 모두 믿으면 안 된다. 특히 decision, approval, risk 관련 노드는 전문가 검수가 필요하다.

검수 우선순위:

| 우선순위 | 조건 |
|---|---|
| P0 | `DecisionGate`, `BusinessRule`, `ApprovalCondition`, `Risk` |
| P1 | confidence 0.75 미만 |
| P1 | canonicalization에서 여러 후보가 병합된 노드 |
| P1 | 에이전트 실행에 직접 영향을 주는 rule |
| P2 | 단순 용어, 설명, 참고 개념 |

검수 항목 예시:

```json
{
  "reviewItemId": "review://rule/go-nogo-pwin-risk",
  "priority": "P0",
  "candidate": "bpdo://rule/go-nogo-pwin-risk",
  "issue": "Pursuit Decision 판단 기준이 실제 Shipley gate 기준과 일치하는지 확인 필요",
  "options": ["approve", "edit", "reject", "needs-more-evidence"],
  "status": "pending"
}
```

## 14. 에이전트 적용 방식

일반 RAG는 문서 chunk만 검색한다. 반면 온톨로지 결합 에이전트는 다음 경로를 따라 근거를 찾는다.

예: 입찰 참여 여부 판단

```text
AEO: make-bid-decision
  usesRule
BPDO: go-nogo-pwin-risk rule
  requiresArtifact
BPDO: Pwin Scorecard, Risk Register
  operationalizes
L1SO: PCF 3.5.3.5 전략·사업계획 검증
  requiresCompetency
L1SO: NCS 수주전략수립
```

이렇게 하면 에이전트 산출물이 단순 생성물이 아니라, 표준 프로세스와 전문가 규칙에 근거한 결과가 된다.

## 15. 실험 설계

### H1: 온톨로지 구축 성능

목표: L1SO, BPDO, alignment relation을 얼마나 정확히 구축하는지 평가한다.

비교군:

| 방법 | 설명 |
|---|---|
| Vanilla LLM | 문서에서 바로 triple/rule 추출 |
| JAO-constrained | JAO schema에 억지로 맞춤 |
| EDC-style | 추출 후 정의와 정규화 |
| Ontology Stack | L1SO/BPDO/AEO를 분리 구축하고 alignment로 연결 |

지표:

- L1SO 계층 정확도
- BPDO class/relation F1
- BusinessRule frame F1
- Alignment accuracy
- Evidence traceability
- Schema valid rate

최소 graph:

```text

  PCF 3.5.3.3 RFP/RFQ 검토
  PCF 3.5.3.4 경쟁 분석 수행

  analyze-rfp
```

성공 기준:

- 모든 산출물이 schema validation 통과
- Go/No-Go 판단의 모든 criterion이 evidence를 가짐
- BPDO rule이 최소 하나 이상의 L1SO 표준 노드와 연결됨
- AEO action이 어떤 BPDO rule을 사용했는지 trace로 남음
- 전문가 기준 명백한 hallucination이 10% 이하

## 18. 주의사항

1. APQC와 Shipley 원문은 외부 공개하지 않는다.
2. 논문에는 schema, 통계, synthetic example, 평가 결과 중심으로 공개한다.
3. JAO는 참고 모델이지 최종 스키마가 아니다.
4. `05_mappings`는 검증 전 자동 매핑이므로 정답 edge로 사용하지 않는다.
5. 이 연구의 핵심은 단순 KG 구축이 아니라 `표준 온톨로지 + 도메인 규칙 온톨로지 + 에이전트 실행 온톨로지`의 연결이다.
6. 성능 평가는 QA 정확도보다 업무 산출물 품질, 요구사항 누락률, 근거 추적률로 해야 한다.
