# PARS-RF + Kiwi

최종 방법론 상세 문서 · 수주·제안 문서 질의응답 · 2026.10.05

질문의 세부 요구를 보존해 근거 후보를 넓히고, 원 질문과 원문의 직접 관련성으로 최종 근거를 선택하는 방법

### 최종 선정

최종 제안 방법은 PARS-RF(PARS Relevance-First) + Kiwi다. 실행 식별자는 PARS_REFINED, 최종 선택 설정은 CE_TOP5다. Kiwi와 고정 규칙으로 Aspect를 추출하고, 질문·Aspect 후보 합집합을 원문 Cross-Encoder로 재정렬한 뒤 선택된 원문으로 답변을 생성·검증한다. 새로운 기초 모델을 학습하거나 파인튜닝한 방법은 아니다.

### 이 문서의 범위

설계 목적, 데이터와 지식 그래프, 추출 규칙, 수식, 실행 순서, 실제 사례, 평가 방법, 최종 메인 테이블, 처리 시간·API 비용, 구성요소 비교와 발표 질의응답을 설명한다. 메인 테이블은 요청한 11개 방법만 포함한다. 구성요소 비교는 별도 해석 표로 제공한다.

수치 기준은 2026년 10월 2일 완료 결과다. 10월 5일의 작업은 발표 문서 제작이며 새로운 성능 실험을 수행한 날짜가 아니다. 10월 1일의 실제 사례와 개발 선택 기록은 해당 시점을 표시해 사용한다. 450문항의 새 평가 결과로 해석하지 않는다.

### 핵심 관측값

| 항목 | PARS-RF + Kiwi |

| Recall@5 | 76.90 / 검색 Gold 175문항 |
| BLEU-4 · ROUGE-L · BERTScore | 27.63 · 47.51 · 92.80 / 답변 178문항 |
| warm 검색 평균 | 243.26ms |
| 온라인 평균 · P95 | 4.56초 · 5.73초 / 동일 표본 30문항 |
| 온라인 API 비용 | 30문항 합계 $0.010801 / 사용량 기반 추정 |

### 결론의 경계

Aspect를 포함한다는 연구 설계 요구에 따라 이 구성을 최종 채택했다. 모든 조건에서 가장 높은 성능이라는 뜻은 아니다. Aspect 후보 확장을 제거한 조건의 점추정이 더 높았으므로, Aspect 자체의 성능 이득이나 모든 요구 충족은 현재 평가에서 입증되지 않았다.

## 01 연구 문제와 설계 원칙

왜 Aspect를 사용하고, 왜 최종 선택은 원문 관련성으로 하는가

### 문제 설정

수주·제안 질문은 절차, 대상, 이유, 시점, 특성 또는 예외를 함께 물을 수 있다. 전체 질문과 비슷한 원문 하나를 찾는 것만으로 모든 요구에 답할 수 있다고 보장하기 어렵다. 이 문제의식은 설계 동기이며 일반 Dense RAG가 항상 실패한다는 실험 결과는 아니다.

Aspect는 단순 명사 키워드가 아니라 독립적으로 답해야 할 정보 요구를 표현하는 검색 단위다. 예를 들어 진행 방식과 갖춰야 할 특성을 함께 묻는 질문에서는 두 정보 요구를 구분한다. 시간·부정·수량·예외는 가능하면 해당 요구에 붙여 의미를 보존한다.

### 세 가지 역할 분리

| 단계 | 역할 | 주의점 |
| --- | --- | --- |
| Aspect | 세부 요구별 후보 검색 경로 제공 | 추출 정확성과 실제 후보 개선은 별도 검증 대상 |
| 지식 그래프 | 업무 맥락에 따른 약한 점수 보정과 직접 뷰 제공 | 그래프 연결 자체를 사실의 증명으로 쓰지 않음 |
| Cross-Encoder | 원 질문과 후보 원문을 함께 읽어 최종 순위 결정 | Aspect마다 근거 하나를 강제로 배정하지 않음 |

### 기존 방법과의 관계

기존 PARS-KG-RAG는 PCF 경로·Aspect 직접 경로·속성 관계 경로를 결합하고 CE와 MMR을 사용했다. 직전 PARS-Cover는 가변 Aspect를 도입하고 관련성·포괄성의 greedy 집합 선택을 사용했다. PARS-RF는 가변 Aspect를 유지하면서 후보 합집합과 CE Top5 선택으로 정제했다.

최종 PARS-RF에는 RRF, MMR, coverage 보너스를 추가하지 않는다. 따라서 이전 방법 대비 변화 전체를 Aspect 상한 해제 하나의 효과로 설명할 수 없다. 이번 최종 선정에서도 A01의 높은 점수를 숨기지 않고 구성요소 비교로 보존한다.

### 발표용 정의

“질문 전체로 중요한 근거를 찾고 세부 요구로 후보를 보완합니다. 업무 그래프로 관련성을 약하게 보정한 뒤, 원문을 다시 읽는 모델이 최종 근거를 고릅니다. 답변의 사실 근거는 그 원문으로 제한합니다.”

## 02 데이터와 지식 그래프

오프라인 준비물과 온라인에서 사용하는 정보

| 단위 | 고정 snapshot 규모 | 역할 |
| --- | --- | --- |
| EvidenceSpan | 1,525 | 최종 검색·인용·답변의 원문 단위 |
| PCFProcess | 2,017 | 업무 프로세스 분류 계층 |
| TaskFrame | 12 | 정규화된 업무 유형 |
| TaskMention | 314 | 원문에서 추출한 업무 표현 |
| Fact | 2,319 | 원문에 연결된 구조화 사실 |
| 직접 검색 뷰 | 5,968 | 원문·Fact·업무 속성의 검색 표현 |

수치는 실험에 사용한 고정 snapshot을 뜻한다. 이후 변경된 외부 데이터베이스의 현재 규모를 의미하지 않는다. 원문은 식별자와 출처 메타데이터를 보존하며, 검색용 표현을 최종 답변의 새 사실로 취급하지 않는다.

### 연결 구조

PCF는 CHILD_OF 계층으로 연결된다. TaskFrame은 MAPS_TO_PCF, ALSO_MAPS_TO_PCF, HAS_PCF_CONTEXT로 PCF와 연결된다. TaskMention은 MEMBER_OF로 TaskFrame에 속한다. Fact와 TaskMention의 SUPPORTED_BY 관계는 해당 원문 근거로 이어진다.

### 직접 뷰

| 뷰 유형 | 수 |
| --- | --- |
| 원문 | 1,525 |
| Fact 주장 / 지식 기능 | 1,751 / 1,751 |
| Fact 조건 | 383 |
| TaskMention 기본 / 대상 / 결과 | 280 / 266 / 12 |
| 합계 / 고유 문자열 | 5,968 / 5,826 |

Fact 뷰는 주어·술어·목적어·주장·조건을, TaskMention 뷰는 업무·행위·대상·결과를 표현한다. 조건만 떼어내지 않고 기본 주장이나 업무 표현을 함께 붙인다. 실제 존재하는 필드만 쓰며, 허용된 직접 근거 연결에 한정한다.

여러 원문에 연결된 속성의 적용 범위를 확인할 수 없으면 관련 속성 뷰를 보수적으로 제외한다. 원문 뷰만 있는 근거 357개도 검색 대상에 남는다. 그래프에 연결되지 않았다는 이유로 근거를 제거하지 않는다.

## 03 Kiwi Aspect 추출

원 질문의 정보 요구와 조건을 보존하는 규칙 기반 처리

### 입력과 출력

입력은 원 질문뿐이다. 정답·Gold 근거·참조답·질문 ID·검색 결과를 추출 입력으로 사용하지 않는다. AdaptiveAspectExtractor는 Kiwi 형태소와 원문 위치를 분석하고, 원문 span을 이어 붙인 search_text 및 추적 정보를 반환한다.

| 순서 | 처리 |
| --- | --- |
| 1 | 무엇·어떤·언제·어떻게·왜 등의 정보 요구 단서와 병렬 연결을 찾는다. |
| 2 | 병렬 경계 양쪽에 정보 요구 단서가 있을 때 요구 구문을 나눈다. 접속사만으로 나누지 않는다. |
| 3 | 원문 요구 구문을 보존하고 규칙에 따라 주제 앵커를 상속한다. |
| 4 | 시간·부정·수치·예외 조건을 찾아 관련 요구에 연결한다. |
| 5 | 내용 형태소·조건·의문 단서의 서명이 같은 표현만 보수적으로 통합한다. |
| 6 | 분해할 수 없으면 원 질문 전체를 하나의 Aspect로 사용한다. |

### 조건 연결과 추적 가능성

같은 요구 구문 안의 조건은 local, 공유 범위가 모호한 외부 조건은 shared_unresolved로 기록한다. 불명확한 범위를 논리적으로 해결했다고 단정하지 않는다. source_spans, anchor_spans, condition_links, constraint_spans, selection_reason을 저장해 출처와 처리 이유를 확인할 수 있다.

```text
search_text = 원문 앵커 | 추가 조건 span | 원문 요구 span
A(q) = {a1, a2, ..., am}
추출 경로: uncapped=True / 검색 경로: aspect_limit=None
```

### 가변 개수의 의미와 현재 한계

최대 3개를 강제하지 않지만 항상 여러 Aspect를 만드는 것도 아니다. 실제 210문항에서는 1개 200문항, 2개 10문항이었다. 복잡한 다중 요구에서의 효과를 검증하기에는 표본이 제한적이다. 규칙의 주제 상속과 의미 중복 판정도 완전하지 않다.

Kiwi 자체가 의미 이해형 Aspect 모델은 아니다. 형태소 분석과 프로젝트 규칙의 조합이다. 추출 평균 3.256ms는 평가 178문항을 각 5회 측정한 값이며 전체 서비스 응답시간과 구분한다.

## 04 질문 관련성과 그래프 보정

R은 질문 전체, M은 개별 Aspect를 위한 점수

### 기호

| 기호 | 의미 |
| --- | --- |
| q / e / ai | 원 질문 / 원문 근거 / i번째 Aspect |
| V(e) | 근거 e의 원문 및 직접 연결된 허용 검색 뷰 |
| p(e) | 선택 PCF와 근거의 직접 매핑 PCF 간 거리 기반 점수 |
| t(e) | 근거에 연결된 선택 TaskFrame 중 최고 정렬 점수 |
| g(e) | 0.9–1.0 범위의 약한 그래프 보정 계수 |

### 질문 전체의 관련성

```text
Semantic(q,e) = 0.9 × 본문 유사도 + 0.1 × 메타데이터 유사도
H(q,e) = 0.75 × Semantic(q,e) + 0.25 × 정규화 BM25(q,e)
g(e) = 0.9 + 0.1 × [0.5 × p(e) + 0.5 × t(e)]
R(q,e) = g(e) × H(q,e)
```

PCF는 identity·description·path 유사도를 0.35·0.45·0.20으로 결합해 Top3를 선택한다. TaskFrame은 의미 점수와 PCF prior를 0.75·0.25로 결합해 총 Top3를 선택한다. 연결 후보가 부족하면 의미 순위에서 채우는 spec_fill_missing 정책을 유지한다.

p(e)는 선택 PCF에서 직접 매핑 PCF까지의 그래프 거리 d에 대한 1/(1+d)의 최댓값이며 연결이 없으면 0이다. t(e)도 해당 연결이 없으면 0이다. 그래프 보정은 원문 검색의 약한 상대적 조정이고, 범주 불일치 시 후보를 차단하는 필터가 아니다.

### Aspect별 직접 뷰 일치도

```text
M_i(e) = g(e) × max { clip(cos(ai,v), 0, 1) : v ∈ V(e) }
```

각 Aspect를 근거의 여러 검색 뷰와 비교하고 가장 높은 일치도를 사용한다. 많은 Fact를 가진 근거가 단순 합산으로 유리해지는 방식이 아니다. 이 유사도와 그래프 연결을 답변 지지 확률이나 정답 판정으로 해석하지 않는다.

## 05 후보 합집합과 원문 재정렬

Aspect는 후보 발굴, CE는 최종 근거 선택

### 후보 구성

```text
C(q) = Top40_e R(q,e) ∪ Union_i [Top20_e M_i(e)]
|C(q)| ≤ min(|E|, 40 + 20m)
```

질문 전체가 제안한 40개와 각 Aspect가 제안한 20개를 Evidence ID 기준으로 합치고 중복을 제거한다. 40·20은 근거 수이지 Aspect 수가 아니다. 점수 동률은 Evidence ID 순서로 결정한다. 원문 한 개가 여러 Aspect를 지지할 수도 있다.

10월 1일 정제 실행의 210문항에서 후보 수는 40–70개, 평균 44.76개였다. 재정렬한 질문–원문 쌍은 9,399개다. 이 수치는 당시 입력의 실제 분포이지 새로운 질문에도 적용되는 고정 상한은 아니다.

### Cross-Encoder 입력과 선택

```text
z(q,e) = CrossEncoder(q, original_text(e))
r(q,e) = sigmoid(z(q,e))
S(q) = Top5_{e ∈ C(q)} r(q,e)
```

BAAI/bge-reranker-v2-m3의 고정 revision을 사용한다. 입력은 원 질문과 후보 원문이며 그래프 속성 텍스트를 추가 사실처럼 붙이지 않는다. sigmoid는 순서를 보존하는 변환이며 보정된 사실 지지 확률이 아니다.

실행은 fp16, batch 32, 최대 512토큰이다. 정제 실행에서 66쌍, 49문항에 입력 길이 제한이 적용됐다. CE 입력 잘림과 답변 context 예산은 별개다. 최종 방식은 CE 점수 순서의 Top5이며 coverage 보너스·RRF·MMR을 사용하지 않는다.

### 계산량과 구현 범위

Aspect 수 m, 직접 뷰 수 V, 차원 d에 대해 뷰 비교는 대략 O(mVd)다. 후보 점수 정렬과 후보 수만큼의 CE 연산이 추가된다. 첫 점수 계산은 전체 근거·뷰에 대한 계산으로, 대규모 ANN 검색으로 소개하면 안 된다. 공통 adaptive runtime의 사용하지 않는 Cover 계산 일부도 남아 있어 완전히 최소화된 실행기는 아니다.

## 06 답변 생성과 근거 검증

검색용 그래프 표현과 답변의 사실 근거를 구분

### 원문 context

선택한 원문 최대 5개에 title·page·section 등 출처와 로컬 인용 ID E1–E5를 붙인다. 공통 예산은 7,000자다. 예산을 초과하면 원문을 몰래 자르거나 근거를 버리는 대신 오류로 처리한다. 메타데이터와 PCF 라벨은 출처·분류 정보이며 추가 사실의 근거가 아니다.

### 생성 호출

gpt-4o-mini-2024-07-18, temperature 0, top_p 1, 최대 출력 350토큰을 사용한다. 원문만 근거로 한국어 한두 문장으로 직접 답하고, 조건·부정·수량·예외를 유지하도록 지시한다. 근거가 부족하면 INSUFFICIENT와 제한사항을 반환한다.

| 출력 | 필드 |
| --- | --- |
| 초안 | answer / citations / status / limitation |
| 검증 | supported / corrected_answer / supported_citations / unsupported_claims / limitation |

### 검증 호출과 저장

같은 모델에 질문·동일 원문·초안을 제공해 주장과 인용을 점검한다. 검증기는 참조 정답을 보지 않으며, 원문에 없는 주장은 제거하거나 수정한다. 최종 답변은 corrected_answer다. 실제 전달되지 않은 인용 ID는 로컬 검증에서 거부한다.

초안이 ANSWERED이고 검증 supported가 참이며 유효한 인용이 있어야 최종 상태도 ANSWERED가 된다. 실제 실행 계약은 JSON schema와 로컬 인용 검사에 의해 제한된다. 원문 안의 지시문은 따를 명령이 아니라 인용된 데이터로 취급한다.

### 기대 효과와 한계

검증은 조건 누락과 근거 없는 확장을 줄이려는 장치다. 동일 모델의 오류가 반복될 수 있어 사람 평가나 독립적인 사실성 판정기를 대체하지 않는다. 검증 성공률이나 유효한 JSON 비율을 정확도와 혼동하지 않는다. 출력 350토큰·한두 문장 제한은 긴 복수 요구의 충분한 서술을 어렵게 할 수 있다.

## 07 실제 질문의 처리 사례

## 11 지표와 결과 읽는 법

검색 적합성과 답변 유사도는 다른 평가 축

```text
Hit@1(q) = 1[첫 검색 근거 ∈ Gold(q)]
Recall@5(q) = |Top5(q) ∩ Gold(q)| / |Gold(q)|
MRR@5(q) = 1 / 첫 Gold 근거 순위 (Top5 내 없으면 0)
```

검색 지표는 Gold가 있는 문항의 값을 평균하고 100을 곱한다. Gold가 다섯 개보다 많아도 Recall 분모를 다섯으로 줄이지 않는다. 따라서 Top5라는 예산 자체가 회수율 상한을 만들 수 있다.

| 지표 | 의미 | 해석 한계 |
| --- | --- | --- |
| BLEU-4 | Kiwi 토큰화 후 1–4그램 중첩의 corpus 지표 | 문장별 BLEU의 단순 평균이나 사실 정확도가 아님 |
| ROUGE-L | 최장 공통 부분수열 기반 F1의 문항 평균 | 표현이 비슷해도 내용이 틀릴 수 있음 |
| BERTScore | 고정 XLM-R large layer 17 기반 문맥 유사도 | 92.80이 사실 정확도 92.80%라는 뜻은 아님 |
| P95 응답시간 | 관측 응답시간의 95백분위 | 30문항·1회 실행으로 꼬리 지연 추정은 불안정할 수 있음 |

### 핵심 비교

Dense RAG에 CE를 추가하면 Recall@5가 60.95에서 73.78로 증가한다. PARS-RF + Kiwi는 76.90이다. 이 관측은 재정렬을 포함한 강한 기준과 비교해야 함을 보여주지만, 구성요소별 원인 분리를 대신하지 않는다.

LLM-only와 FullDoc의 낮은 답변 점수는 이 데이터·프롬프트·출력 예산에서의 결과다. 문서가 많을수록 항상 좋다거나 FullDoc이 성능 상한이라는 가정을 두지 않는다. 낮은 BLEU만으로 모든 답변이 사실적으로 틀렸다고 단정할 수도 없다.

### 불확실성

LLM 추출기 비교의 검색·답변 차이에 대한 paired 95% 구간은 모두 0을 포함하거나 경계가 0이다. 이 구간은 문서·섹션 군집 bootstrap 10,000회이며 다중 비교 보정 없는 탐색적 결과다. 다른 모든 비교도 동일한 검정을 통과했다고 확대 해석하지 않는다.

| 누적 GPT / 임베딩 | 7.97242155 / 0.02893862 |

FullDoc은 인용 개수 검증을 기존 조건에 맞춰 전체 30문항을 재측정했다. 메인 표는 수정 후 결과다. 제외한 최초 측정 비용 $0.83386965는 누적 지출에 포함되므로 메인 표 비용 열의 합과 누적 지출은 다르다.

10월 5일 문서·발표 자료 제작에는 모델 API를 호출하지 않았다. 문서에 사용한 라이브러리와 글꼴 다운로드는 실험 API 지출과 별개다.

A03은 g=1로 두지만 직접 뷰·Aspect·CE를 유지한다. A04는 Aspect 매칭에서 Fact·속성 뷰만 제외하고 질문 점수의 그래프 보정은 유지한다. A04의 Hit@1 76.00, MRR@5 84.10은 전체 조건 중 가장 높은 점추정이다.

## 14 Kiwi와 LLM Aspect 비교

추출기만 바꾸었을 때의 품질·시간·비용

| --- | --- | --- |

LLM은 질문 원문의 substring을 사용해 Aspect를 구성하도록 제한했다. 추출 입력에 정답·Gold·검색 결과를 주지 않는다. 원문 span 또는 형식 검증에 실패한 3건은 원 질문 하나로 fallback하고 성능·시간·비용 분모에 포함했다.

### 관측된 변화

PARS-RF의 Recall 변화는 +0.286%p, ROUGE-L 변화는 +0.036점이다. 평가 178문항 중 Top5와 context가 바뀐 문항은 3개였다. Aspect-View에서는 2개였고 Recall은 77.09로 같았다. 원문 span 조건을 통과했다고 의미적으로 올바른 요구 분해가 보장되는 것은 아니다.

### 재사용 범위와 비용 해석

추출은 전체 210문항에서 수행해 두 LLM 조건이 공유했다. 모델·프롬프트·context가 완전히 같으면 기존 답변·검증을 재사용해 706회 캐시 hit가 있었다. 신규 답변·검증은 각각 3회였고, 이 때문에 추가 비용 $0.01358844를 모든 문항 독립 실행 비용처럼 읽으면 안 된다. 온라인 30문항 표본은 별도로 새 호출한 측정이다.

### 최종 선택

현재는 Kiwi를 유지한다. LLM 추출에서 뚜렷한 품질 우위가 확인되지 않았고, 온라인 평균은 약 1.45초, 30문항 비용은 약 15.6% 증가했다. 복합 요구·조건 질문에서 독립적인 사람 검수와 근거 회수 비교를 수행한 뒤 교체 여부를 다시 판단하는 것이 적절하다.


## 17 발표 예상 질문과 답변

기술 설명과 결과 해석을 준비하기 위한 문답

### 왜 성능이 더 높은 Aspect 제거 조건을 최종안으로 쓰지 않았나요?

Aspect를 포함한 요구별 후보 검색을 연구 대상으로 유지하는 설계 결정입니다. A01이 더 높은 결과도 공개하며, Aspect 자체의 이득은 아직 확정하지 않습니다.

### Aspect-View가 더 가볍다면 왜 PARS-RF인가요?

최종 연구 구조를 기존 PARS-RF로 고정하고 그래프 보정의 경량 변형으로 비교합니다. 두 방법의 품질 차이는 작으며 M01의 확정적 우위를 주장하지 않습니다.

### Aspect와 단순 키워드는 무엇이 다른가요?

질문이 요구하는 정보 구문과 관련 조건을 원문 span으로 보존합니다. 다만 규칙 기반이므로 완전한 의미 이해나 정확한 분해를 보장하지 않습니다.

### 그래프가 틀리면 원문을 못 찾나요?

그래프를 필수 통과 필터로 쓰지 않습니다. 전체 원문에 대한 검색과 0.9–1.0의 약한 보정을 사용하므로 그래프 밖 근거도 후보가 될 수 있습니다.

### 40개·20개·5개는 무엇인가요?

질문 후보 40개, 각 Aspect 후보 20개, 최종 원문 5개입니다. Aspect 개수는 제한하지 않습니다.

### LLM으로 Aspect를 뽑으면 더 좋지 않나요?

현재 PARS-RF Recall은 0.286%p 증가했지만 구간의 하한이 0이며 답변 개선도 작습니다. 지연·비용을 고려해 Kiwi를 유지합니다.

### BERTScore 92.80이면 정확도가 92.80%인가요?

아닙니다. 참조답과의 문맥 유사도입니다. 사실성·실무 유용성·요구 충족에는 별도 평가가 필요합니다.

### 최종 답변 검증은 정답을 보나요?

보지 않습니다. 동일 원문과 생성 초안만 검사합니다. 사람 검수나 독립 정답 판정기를 대체하지 않습니다.

You are a grounded Korean QA assistant for proposal work.

## 19 4장 발표 운영안

권장 7–9분 · 상세 대본은 PPT 발표자 노트에도 포함

### 1장 · 문제와 접근

오늘 소개할 최종 방법은 PARS-RF + Kiwi입니다. 수주·제안 질문에는 진행 방식, 특성, 조건처럼 서로 다른 요구가 함께 들어갑니다. 그래서 질문 전체의 검색 후보와 각 요구의 후보를 함께 사용하도록 설계했습니다. 여기서 Aspect는 단순 키워드가 아니라 원문에서 추출한 정보 요구입니다. 그래프는 업무 맥락을 약하게 보정하고, 최종 답변 근거는 실제 원문으로 제한합니다. 이 방법은 새 모델 학습이 아니라 검색과 근거 선택 절차의 설계입니다. 평가 대상은 기존 210문항 중 답변 178문항, 검색 Gold 175문항이며 독립 시험셋은 아닙니다. Aspect를 유지한다는 설계 결정과 성능상 항상 최적이라는 주장은 구분하겠습니다.

### 2장 · 알고리즘

먼저 Kiwi와 고정 규칙으로 원 질문의 요구 구문을 추출하고 조건을 연결합니다. Aspect 개수의 고정 상한은 없습니다. 질문 전체에는 의미·어휘 관련성과 PCF·TaskFrame 보정을 적용해 R을 계산합니다. 각 Aspect는 원문과 직접 연결된 Fact·속성 뷰에 대해 M을 계산합니다. R 상위 40개와 각 M 상위 20개의 합집합을 만들고 중복을 제거합니다. 다음으로 원 질문과 후보 원문만 Cross-Encoder에 넣어 Top5를 선택합니다. Aspect별 근거를 강제로 하나씩 배정하거나 coverage 보너스를 주지 않습니다. 이후 동일 GPT-4o mini로 생성과 근거 검증을 수행합니다. 실제 예시 질문에서는 두 요구로 70개 후보가 생겼고, 하나의 원문이 두 요구를 함께 지지했습니다. 그래프에 연결되지 않은 원문도 제거하지 않습니다.

### 3장 · 최종 메인 테이블

이 표는 핵심 베이스라인 다섯 개, 보조 베이스라인 네 개, 최종 제안 방법과 LLM 추출기 비교를 포함한 11조건입니다. 굵은 행은 최고값 표시가 아니라 최종 채택을 뜻합니다. 가장 중요한 단순 기준은 Dense+CE입니다. Recall@5는 Dense+CE 73.78에서 PARS-RF + Kiwi 76.90으로 3.12퍼센트포인트 높습니다. ROUGE-L 변화는 약 0.43점이며 통계적으로 확정된 답변 품질 우위라고 말하지 않습니다. LLM 추출은 Recall 77.18로 조금 높지만 응답시간은 4.56초에서 6.01초로 늘었습니다. 검색 시간은 warm 측정이고, 전체 응답은 같은 30문항의 신규 호출 측정입니다. 비용은 30문항 합계이며 구축·GPU 비용은 제외합니다. FullDoc과 LightRAG의 동시성 차이, 공유 KG 비교 범위, 기존 생성 실패도 해석에 포함해야 합니다.

### 4장 · 해석과 결론

최종적으로 Aspect를 포함하는 PARS-RF + Kiwi를 유지합니다. 추출기만 LLM으로 바꾼 실험에서 뚜렷한 품질 이득이 확인되지 않았고 응답과 비용이 증가했기 때문입니다. 동시에 불리한 결과도 중요합니다. 메인 표 밖 구성요소 비교에서는 Aspect 후보 확장을 제거한 조건의 Recall이 77.95로 최종 방법보다 높았습니다. 따라서 Aspect 덕분에 성능이 향상되었다고 단정하지 않습니다. 실제 Kiwi 추출은 210문항 중 200문항이 한 요구였기 때문에 다중 요구에서의 효용을 판단할 자료가 부족합니다. 다음 검증은 새 문서의 복합 요구·조건 질문, 사람의 요구 충족 평가, 동일 동시성 반복 측정입니다. 현재 기여는 요구별 후보 확장과 원문 관련성 선택을 분리한 재현 가능한 구조와 비교 결과라고 정리하겠습니다.
